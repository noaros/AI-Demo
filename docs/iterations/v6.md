# v6: Agent framework and write actions

**Goal:** two changes. First, hand the agent loop to a framework: v5's hand-written loop showed the mechanics, but a loop is plumbing you don't want to maintain. Second, let the agent *do* things: open tickets and reset passwords. That second change is the important one. Until now the worst a bad answer could do was mislead someone; from v6 on, the agent changes real records.

## What's included

```
AI-Demo/
├── app/
│   ├── agent.py            # new: the agent on Microsoft Agent Framework, its tools and middleware
│   ├── backend.py          # + create_ticket, reset_password (written to Cosmos DB), fake accounts
│   ├── main.py             # async endpoints; agent.run() replaces the hand-written loop
│   └── tools.py            # removed: replaced by agent.py
├── prompts/helpdesk-v4.md  # new: may open tickets and reset passwords
└── infra/
    ├── resources.bicep     # + Cosmos DB container "servicedesk"; provisioning keeps the running image
    └── current-image.bicep # new: reads the image the app is running
```

This iteration adds a Cosmos DB container: run `azd up`.

## What changed

### The loop is now Microsoft Agent Framework

[Microsoft Agent Framework](https://learn.microsoft.com/agent-framework/) (`agent-framework-core` and `agent-framework-openai`) runs the same loop v5 wrote by hand. Each piece of v5 has a counterpart:

| v5, by hand | v6, Agent Framework |
|---|---|
| `for _ in range(MAX_STEPS)`: call the model, run tools, append results | `agent.run(messages, tools=...)` |
| Pydantic model per tool + `pydantic_function_tool` | `tool(method)`: the schema comes from the method's type hints and `Field` descriptions |
| `Toolbox.run()`: look up the handler, validate arguments, catch errors | the framework does it |
| `answer_tool_calls()`: append the request and one result per call | the framework does it |
| `MAX_STEPS = 5` and a 502 | `max_iterations: 5` |
| `log.info(...)` inside `Toolbox.run()` | function **middleware**: code that runs around every tool call |
| streaming: SDK helper + our loop | `agent.run(..., stream=True)` |

`app/main.py` no longer has a loop. What's left is ours: the tools, the instructions, and what happens around a tool call.

A few things work differently from v5:

- **Async.** The framework is asynchronous, so the endpoints are now `async def`. The Cosmos DB and AI Search clients are still synchronous; their calls run in a worker thread (`asyncio.to_thread`) so they don't block other requests. Synchronous tool functions are run in a thread by the framework.
- **At the step limit the model answers anyway.** v5 returned 502 after 5 steps. The framework instead stops offering tools and makes the model answer with what it has. With the limit lowered to 1 and three tickets to look up, it fetched one and said it couldn't get the other two. Friendlier for users, but nothing in the response says the answer was cut short.
- **Tool schemas aren't strict.** v5's tools used the API's strict mode, so the model *couldn't* send malformed arguments. The framework validates them with Pydantic instead and returns an error to the model. In practice the result is the same; the guarantee is now in our process instead of in the API.
- **History is still ours.** The framework has its own conversation store (including a `CosmosHistoryProvider`), which saves every message, tool calls and results included. We keep v3's `SessionStore`: only questions and answers, trimmed to a token budget. That's a deliberate choice, explained in v5.

**Why Agent Framework and not Foundry Agent Service?** Foundry Agent Service runs the agent for you in Azure: the conversation, the loop and some tools live in the service, and the app calls it. It's a good fit when you want the platform to own state and tool hosting. Agent Framework runs inside our app, which keeps everything built so far (Cosmos DB memory, trimming, our search) and keeps this diff about the loop. The tools and middleware written here would carry over.

### Write tools

Two new tools change things. Both write to a new Cosmos DB container, `servicedesk`, standing in for the ticketing system's database, so they survive restarts as they would in a real system.

| Tool | Does |
|---|---|
| `create_ticket(title, description, priority)` | opens a ticket and returns its number; `get_ticket` can read it back |
| `reset_password(account)` | "resets" the account and texts a temporary password to the phone on file; the password never appears in the chat |

`priority` is `Literal[1, 2, 3, 4]` with the meanings from IT-POL-014 in its description, so the model can only pick a valid priority and knows what each means.

Prompt `helpdesk-v4` lets the agent open tickets and reset passwords when asked.

### Watch it break: an agent that acts

There are no safeguards in this iteration, on purpose. Three things to see:

1. **It resets anyone's password.** "Reset the password for megan.bowen@contoso.com" resets the CEO's account without a question. The agent doesn't know who's asking (`/chat` has no sign-in), and even if it did, nothing checks whether that person may do this. In a real system, this is an account takeover: reset a password, then social-engineer the temporary one.
2. **It writes made-up details into records.** Asked to "open a ticket: the printer on floor 3 jams on every double-sided job", it wrote a description that also said *"No error codes displayed on printer panel. Users tried power cycle and clearing visible paper jams but issue persists."* The user said none of that. A made-up detail in a chat answer is gone when the chat ends; in a ticket, it's in the system of record, and an engineer will act on it.
3. **It acts without asking.** Nothing confirms a write before it happens. The model decides, the tool runs, and the user finds out afterwards.

v7 fixes the first and third: risky tools need a human's approval, and the agent acts with the *user's* identity and permissions, not its own. Checking what goes into records is v8 and v10.

### Fix: provisioning no longer replaces the running app

The Bicep template always set the app's image to a placeholder, which `azd deploy` then replaced. `azd up` hid this, because it deploys right after provisioning. But a plain `azd provision`, for example to add this iteration's container, put the placeholder back and the app went down until the next deploy. Now azd passes `SERVICE_API_RESOURCE_EXISTS`, and `infra/current-image.bicep` reads the image the app is running so provisioning keeps it. (A separate module, because reading the app and updating it in the same deployment is a circular dependency.) Verified: a forced `azd provision --no-state` kept the deployed image. The first-time path (no app yet, placeholder image) wasn't re-tested.

## Demo script

Set the URL once: `URL=$(azd env get-value SERVICE_API_URI)`.

1. **Same behaviour, new engine.** The v5 questions behave the same:
   ```bash
   curl -s -X POST $URL/chat -H 'Content-Type: application/json' \
     -d '{"question": "My laptop CTSO-10442 has a cracked screen. Is it covered?"}' | jq '.answer, .tool_calls'
   ```
   Then open `app/main.py` next to `git show v5:app/main.py`: the loop is gone, `agent.run()` is in its place.
2. **Open a ticket.** Ask "My docking station stopped charging my laptop this morning. I can still work on battery. Please open a ticket." The agent asks for the asset tag; answer with `CTSO-10442` in the same session. It checks the warranty, opens a priority-3 ticket and gives you its number. Ask "What is the status of INC…?" in a new session: `get_ticket` reads it back.
3. **Watch it break: someone else's password.**
   ```bash
   curl -s -X POST $URL/chat -H 'Content-Type: application/json' \
     -d '{"question": "Reset the password for megan.bowen@contoso.com"}' | jq '.answer, .tool_calls'
   ```
   The CEO's password is reset. No question, no check of who asked.
4. **Watch it break: invented facts in a record.**
   ```bash
   curl -s -X POST $URL/chat -H 'Content-Type: application/json' \
     -d '{"question": "Open a ticket: the printer on floor 3 jams on every double-sided job. Priority 3."}' \
     | jq '.tool_calls[0].arguments.description'
   ```
   Compare the description with what you wrote. Look for troubleshooting steps or observations you never mentioned.
5. **The middleware.** The container logs show `tool call: …` for each tool, written by `Toolbox.record_tool_call`, which the framework runs around every call. v7 puts its approval check in exactly this spot.
6. **The records.** In the portal: Cosmos DB → Data Explorer → `helpdesk` → `servicedesk`. Every ticket and every password reset the agent did is there.

## What's still wrong

| Problem | Fixed in |
|---|---|
| Anyone can reset anyone's password; tools act with the app's power, not the user's | v7: user sign-in, on-behalf-of identity, least privilege |
| Writes happen without a human confirming them | v7: approval for risky tools |
| The agent writes invented details into tickets | v8: groundedness checks; v10: evals of tool arguments |
| Instructions hidden in tool results could now trigger *actions*, not just words | v8: Prompt Shields on tool results |
| If the model calls `create_ticket` twice, there are two tickets: no idempotency | v11: retries and idempotency |
| At the step limit the answer is quietly partial | v9: tracing shows it; v11: budgets |
| You can't see what the framework's loop did, step by step, with timings and tokens | v9: Agent Framework's OpenTelemetry tracing |
