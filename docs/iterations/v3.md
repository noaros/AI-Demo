# v3: Memory

**Goal:** let a conversation continue. The model itself remembers nothing between calls: every request has to carry the whole conversation. v3 stores each conversation in Cosmos DB and sends the model as much of it as fits in a token budget.

## What's included

```
AI-Demo/
├── app/
│   ├── config.py           # + AZURE_COSMOS_ENDPOINT, HISTORY_TOKEN_BUDGET (default 2000)
│   ├── memory.py           # new: SessionStore (Cosmos DB) and trim_to_budget
│   └── main.py             # session_id on /chat and /chat/stream, new GET /sessions/{id}
├── infra/
│   └── resources.bicep     # + Cosmos DB (serverless, keys off), data role for the app
├── Dockerfile              # downloads the tokenizer at build time
└── …
```

This iteration adds infrastructure, so run `azd up` (not just `azd deploy`).

## What changed

**Conversations have a `session_id`.** Leave it out and the API starts a new conversation and returns its id. Send it back with the next question to continue:

```json
{"question": "What about on a Mac?", "session_id": "3f2c…"}
```

`/chat` returns it in the JSON body; `/chat/stream` returns it in the `X-Session-Id` header, because the body is plain text.

**The history lives in Cosmos DB, not in the app.** It would be easy to keep it in a Python dict, and that works on your laptop. In production it fails: Container Apps scales to zero when idle and restarts on every deploy, and with two or more replicas the next question may land on one that has never seen the conversation. Keeping state outside the app means any replica can answer any request.

Cosmos DB here is:

- **Serverless:** you pay per request and nothing while it's idle. Right for a demo and for spiky, low-volume apps. Steady heavy traffic is cheaper with provisioned throughput.
- **One document per conversation**, `{"id": <session id>, "messages": [...]}`, with the session id as the partition key. Every read and write goes straight to one document (a *point operation*, about 1 request unit) instead of searching.
- **Append with a patch.** New messages are added with a server-side patch (`add /messages/-`) instead of read, modify, write back. Two requests to the same conversation can't overwrite each other's messages.
- **Auto-deleting:** the container has a 7-day time to live. Cosmos removes a conversation 7 days after its last message. Chat logs contain whatever people typed, often personal data, so how long you keep them is a decision, not an accident.
- **Keys off, like OpenAI:** `disableLocalAuth: true`. The app's managed identity gets the *Cosmos DB Built-in Data Contributor* role. Cosmos has its own data-plane role system (separate from Azure RBAC), and the role is scoped to the `helpdesk` database rather than the whole account.

**Token-window trimming.** A model can only read so much at once (its *context window*), and you pay for every token you send, on every turn. A conversation that grows forever eventually fails, and gets more expensive and slower long before that. So the app:

1. keeps the **full** history in Cosmos DB;
2. before each call, walks back from the newest message and keeps messages until the next one would go over `HISTORY_TOKEN_BUDGET` (2000 tokens by default);
3. drops a leading answer whose question was cut off, so the model never sees an answer to nothing.

Tokens are counted with `tiktoken` using the same tokenizer as gpt-5 models (`o200k_base`), not estimated from characters. The tokenizer file is downloaded in the Dockerfile, so the first user request doesn't wait for it.

The system prompt and the new question are always sent. Only older history gets trimmed. `/chat` reports how many earlier messages the model saw in `history_sent` (`X-History-Sent` header on the stream).

**`GET /sessions/{id}`** returns the full stored conversation, including messages trimmed from what the model sees. It's there to make the demo visible. As v3 stands it's also a weakness (see below).

## Demo script

Set the URL once: `URL=$(azd env get-value SERVICE_API_URI)`. Right after `azd up`, the URL can show Azure's placeholder page for half a minute while the new revision starts (the app connects to Cosmos DB before it serves). Check `curl $URL/healthz` first.

1. **Watch it break: no session.**
   ```bash
   curl -s -X POST $URL/chat -H 'Content-Type: application/json' \
     -d '{"question": "How do I set up a VPN on Windows 11?"}' | jq '.answer, .session_id'
   curl -s -X POST $URL/chat -H 'Content-Type: application/json' \
     -d '{"question": "What about on a Mac?"}' | jq .answer
   ```
   The second answer has no idea what "what about" refers to. That was every conversation in v2.
2. **Watch it hold: same question, with the session.**
   ```bash
   SID=$(curl -s -X POST $URL/chat -H 'Content-Type: application/json' \
     -d '{"question": "How do I set up a VPN on Windows 11?"}' | jq -r .session_id)
   curl -s -X POST $URL/chat -H 'Content-Type: application/json' \
     -d "{\"question\": \"What about on a Mac?\", \"session_id\": \"$SID\"}" | jq '.answer, .history_sent'
   ```
   Now it answers about VPN on macOS, and `history_sent` is 2: the earlier question and answer.
3. **Streaming keeps the conversation going.**
   ```bash
   curl -N -i -X POST $URL/chat/stream -H 'Content-Type: application/json' \
     -d "{\"question\": \"And on my phone?\", \"session_id\": \"$SID\"}"
   ```
   `-i` shows the headers: the same `X-Session-Id` and `X-History-Sent: 4`.
4. **The state outlives the app.** Leave the app idle for about 5 minutes and it scales to zero: no process is running, so nothing is left in its memory. Check, continue the conversation, then check again:
   ```bash
   APP=$(az containerapp list -g rg-<env> --query "[0].name" -o tsv)
   az containerapp replica list -g rg-<env> -n $APP -o table    # empty: scaled to zero
   curl -s -X POST $URL/chat -H 'Content-Type: application/json' \
     -d "{\"question\": \"Which of the steps you gave me needs a certificate?\", \"session_id\": \"$SID\"}" | jq '.answer, .history_sent'
   az containerapp replica list -g rg-<env> -n $APP -o table    # a new replica
   ```
   A process that didn't exist a moment ago answers with the whole conversation in context: it refers back to the steps from the first question. Don't use `az containerapp revision restart` for this: it returns straight away and the old replica keeps answering until the new one is ready, so your next request proves nothing. Then look at the stored conversation:
   ```bash
   curl -s $URL/sessions/$SID | jq
   ```
   Or open the Cosmos DB account in the portal, then *Data Explorer → helpdesk → sessions*.
5. **Trimming.** Run locally with a small budget (see the README for running locally). Answers here are 60–480 tokens each, so 1000 tokens holds about two exchanges:
   ```bash
   HISTORY_TOKEN_BUDGET=1000 uvicorn app.main:app --env-file .env
   ```
   Ask five different questions in one session (VPN, battery, network drive, Outlook password, second monitor). `history_sent` stays at 2–4 instead of growing. Then ask "What was the first thing I asked you in this conversation?" In our run it answered, with confidence, "Outlook keeps asking for my password": the oldest message it could *see*. It doesn't say it can't know. The VPN question is still in `GET /sessions/{id}` (all 12 messages are stored), it just wasn't sent. Trimming isn't only a cost setting: it decides what the model believes the conversation was.

## What's still wrong

| Problem | Fixed in |
|---|---|
| Anyone with a session id can continue that conversation or read it with `GET /sessions/{id}`. Sessions aren't tied to a user | v7: Entra ID user sign-in; sessions belong to the signed-in user |
| Trimming forgets old messages outright; a long conversation loses its early context. Summarising old turns would keep more of it, for an extra model call | Not planned; a trade-off worth knowing |
| Still makes up company facts | v4: grounding with Azure AI Search |
| Stored conversations, and what goes into them, aren't checked for injected instructions | v8: Prompt Shields |
| No traces: you can't see what history was sent or what it cost | v9: OpenTelemetry + Application Insights |
| No rate limits, no per-session token budget | v11: API Management AI gateway, budgets |
| A stream that drops halfway isn't saved, so the user's question is lost too | Acceptable for now; the user just asks again |
