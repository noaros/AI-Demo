# v12: Continuous improvement

**Goal:** make the agent better from what happens in production, not only from what we thought of. v10's golden dataset holds the failures we imagined. Real users find others, and so do attackers. v12 adds two ways for those failures to get into the dataset: users saying an answer was wrong, and an automated red team. Then a fix is proven by the same gate as everything else.

```
user 👎 + comment ─┐                                  ┌─ reviewed by a person ─┐
                   ├─► evals/candidates.yaml (drafts) ─┤                        ├─► golden.yaml ─► CI gate (v10)
red team attack ───┘                                  └─ reproduces? (fails) ──┘
```

## What changed

### Feedback, linked to the trace

Every answer already has a `trace_id` (v9). The conversation now stores it with the answer, and `POST /feedback` takes one:

```bash
curl -X POST $URL/feedback -H "$AUTH" -H 'Content-Type: application/json' -d '{"session_id": "<session_id>",
  "trace_id": "<trace_id>", "helpful": false, "comment": "It should have said this is only for developers"}'
```

You can only rate answers in your own conversations. The feedback is stored in Cosmos DB (`feedback`, one document per answer) **with the question and the answer**: traces deliberately don't record them (v9), and conversations expire after 7 days, but a complaint has to stay readable until someone looks at it. That makes the feedback container personal data with no expiry. In production it needs a retention rule and a place in the privacy notice.

The feedback request's own trace gets `helpdesk.feedback_for` (the answer's trace id) and `helpdesk.helpful`, so Application Insights can join a complaint to everything that happened while answering:

```kusto
let complaints = requests | where customDimensions["helpdesk.helpful"] == "False"
    | project feedback_for = tostring(customDimensions["helpdesk.feedback_for"]);
requests | join kind=inner complaints on $left.operation_Id == $right.feedback_for
| project timestamp, resultCode, duration, tostring(customDimensions["helpdesk.tool_calls"]),
          tostring(customDimensions["helpdesk.cost_usd"]), operation_Id
```

### From complaint to eval case

`python -m evals.from_feedback` reads untriaged thumbs-down feedback, and for each one asks the judge model to draft the rules a good answer would meet, based on the user's comment. The drafts go to `evals/candidates.yaml`, with the trace id, comment and bad answer next to them. It's not in git: it holds what users typed.

**A person reviews every draft.** This was the most important lesson, and the first two complaints show why:

| Complaint | Draft rules | Review |
|---|---|---|
| *"Can I install Zoom?"* → "It should tell me how to request an exception, and who approves it." | "Says how to request an exception…", "Identifies who approves the exception…" | **Rejected.** Zoom is pre-approved in the Company Portal; the answer was right. Promoting this case would train the agent to invent an exception process. |
| *"Can I get admin rights for a day to install a driver?"* → "I'm in Finance. Admin By Request said I'm not eligible. The bot should have told me it's only for developers and IT staff." | "Says Admin By Request is not available to Finance employees…", "Tells them to open a ticket and include the driver name and error messages…" | **Rewritten.** Right in spirit, but rule 1 assumes "Finance", which isn't in the question, and rule 2 is a requirement nobody asked for. |

The reviewed case, now in `golden.yaml`:

```yaml
- id: admin-rights-eligibility
  question: Can I get admin rights on my laptop for a day to install a driver?
  tools: [search_policies]
  cite: [IT-POL-015]
  rubric:
    - Says that temporary admin rights (Admin By Request) are only for developers and IT staff, or asks whether the
      user is one, instead of telling the user they can get them.
  repeat: 3
```

**Then check that it reproduces.** A new case must *fail* on the current version. If it passes, it isn't testing what went wrong. `python -m evals.run --case admin-rights-eligibility --repeat 6` on `helpdesk-v7`: **4 of 6 runs failed.** The answers said "You can get temporary local admin rights for 60 minutes using Admin By Request", every sentence taken from the policy except the one that matters.

None of the general judges noticed. On the same six runs, task adherence was 1.00 and groundedness 4.83 out of 5: each sentence *is* supported by the policy, and it's the condition left out that makes the answer wrong. Only a rule written for this case catches it.

**The fix:** `helpdesk-v8` adds one rule: *"When an excerpt limits who something is for (a role, a team, a type of employee), say who it's for. The start of the conversation doesn't tell you the user's job, so don't assume they qualify: tell them the condition, or ask."* Result: **6 of 6** passed. The full suite, now 20 cases, still passes the gate: 77 of 78 checks (the one failure is v10's known weakness, `injection-subtle-no-offer`), judge means 4.74 / 0.95 / 5.00 / 5.00. Task adherence dipped because the judge failed `general-know-how` once, the run-to-run variation v10 described.

### Red teaming

`evals/red_team.py` runs Microsoft's **AI Red Teaming Agent** (`azure-ai-evaluation[redteam]`, built on the open-source PyRIT) against the real `/chat` endpoint, in-process, as a regular test user, like the evals. It takes harmful requests from Microsoft's safety service for each risk category (violence, hate and unfairness, sexual content, self-harm) and sends each one plain and disguised: Base64, reversed text, Morse code, and known jailbreak prompts. The same service judges each answer. The **attack success rate (ASR)** is the share of attacks that got harmful content out. Attacks that work become draft cases in `candidates.yaml`, marked critical.

It needs an **Azure AI Foundry project**, for the attack prompts and the scoring, and that's where results are uploaded: the project's *Red teaming* page in the Foundry portal. The account and project cost nothing while idle. `.github/workflows/red-team.yml` runs it every Monday against `main`, and the drafts come back as a workflow artifact.

First scan, 2 attack goals per category, 40 attacks:

| | Plain | Base64 | Reversed | Morse | Jailbreak |
|---|---|---|---|---|---|
| Attacks | 8 | 8 | 8 | 8 | 8 |
| Successful | 0 | 0 | 0 | 0 | 0 |
| Stopped by Prompt Shields (v8) | 0 | 1 | 0 | 0 | 3 |
| Stopped by Azure OpenAI's content filter | 4 | 0 | 0 | 0 | 3 |
| The agent refused | 4 | 7 | 8 | 8 | 2 |

ASR 0%. **But reading the transcripts found a bug the score didn't show:** the 7 attacks stopped by Azure OpenAI's content filter came back to the user as **502 "The model is unavailable"**, the outage message from v11. A refusal reported as an outage misleads users and would set off error alerts. Some filter errors don't use the code the agent framework recognises (`content_filter`): one is `bio_policy`, *"flagged for possible biological risk"*. They're now a **400 "Blocked by the content filter"**, recorded as `helpdesk.blocked = content_filter`. Replaying the same attacks: 5 blocked with the new message, and the agent itself refused the other 2. The filter isn't deterministic either.

**What the red team can't test here.** The service also has agent-specific risk categories: prohibited actions, sensitive data leakage, task adherence. For an app like ours (a custom endpoint rather than an agent hosted in Foundry) they don't work: sensitive data leakage is *"only available for agent targets"*, and the other two return no attack goals. So the attacks that matter most for *this* agent stay in our own dataset: injections through tickets, resetting someone else's password. The red team covers the generic harms, not ours.

**PyRIT pins its Python version.** The `[redteam]` extra needs PyRIT 0.11, which doesn't install on Python 3.14. CI uses 3.13. Locally, a separate environment: `uv venv -p 3.13 .venv-redteam`.

## Demo script

With the azd values exported (`set -a; eval "$(azd env get-values)"; set +a`):

1. **A bad answer.** On `v11`, ask `"Can I get admin rights on my laptop for a day to install a driver?"` a few times: some answers tell anyone they can use Admin By Request.
2. **Complain.** `POST /feedback` with the answer's `session_id` and `trace_id`, `"helpful": false`, and a comment.
3. **Draft a case.** `python -m evals.from_feedback`, then read `evals/candidates.yaml`: the draft rules, and the bad answer next to them. Review it: what would you change?
4. **Reproduce.** With the reviewed case in `golden.yaml`: `PROMPT_NAME=helpdesk-v7 python -m evals.run --case admin-rights-eligibility --repeat 6`. It fails on most runs.
5. **Fix and prove it.** The same command with `helpdesk-v8`: 6 of 6. Then the full suite: the gate still passes.
6. **Red team.** `.venv-redteam/bin/python -m evals.red_team` (about 6 minutes), then open the scan in the Foundry portal. Look at the transcripts, not just the ASR:
   ```bash
   jq -r '.[] | "\(.attack_technique)\t\(.conversation[-1].content[:80])"' evals/results/redteam-*.json
   ```

## What's still wrong

| Problem | Fixed in |
|---|---|
| Triage needs a person, so complaints can pile up | It's meant to: the review is the point. Track the backlog (untriaged count) as a metric |
| The feedback container keeps users' questions and answers forever | A retention rule (Cosmos DB TTL), and the privacy notice |
| The red team doesn't test agent-specific risks (unauthorised actions, data leakage) for an app outside Foundry | Our own cases in `golden.yaml`; or host the agent in Foundry Agent Service |
| Red team scoring is a model's judgement, like the eval judges | Read transcripts; promote real findings to deterministic cases |
| The agent still offers the injected CEO password reset (v10) | Open. `injection-subtle-no-offer` tracks it |
| Everything from v11's list: one region except the model, synchronous clients, no deadline when streaming | Open |
