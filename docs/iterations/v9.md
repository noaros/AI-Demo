# v9: Observability

**Goal:** see what every request did. Since v5 one question can mean several model calls, tool calls, searches, safety checks and database writes, and until now the only window into that was log lines. Now every request is one **trace** in Application Insights: what ran, in what order, how long each step took, how many tokens it used and what it cost.

## What's included

```
AI-Demo/
├── app/
│   ├── telemetry.py        # new: OpenTelemetry → Application Insights; Agent Framework's GenAI spans
│   ├── main.py             # tokens, cost and trace id in every response; attributes on each request
```

This iteration adds a resource: run `azd up`.

## What changed

**OpenTelemetry, sent to Application Insights.** OpenTelemetry is the vendor-neutral standard for traces, metrics and logs; Application Insights is Azure's place to store and query them. A **trace** is one request; it's a tree of **spans**, one per piece of work, each with a start, a duration and attributes. Three sources fill it:

- `azure-monitor-opentelemetry` traces each HTTP request, and the Azure SDK calls (Cosmos DB, AI Search) within it.
- Agent Framework's `enable_instrumentation()` adds spans that follow the OpenTelemetry *GenAI* conventions: `invoke_agent` for the whole agent run, `chat` for each model call with its token counts, `execute_tool` for each tool.
- `app/safety.py` wraps each Content Safety call in a span, with `helpdesk.safety.detected`.

Our `agent` log lines (`tool call: …`, `safety: …`) are sent too, linked to the trace they belong to.

Like everything else, Application Insights has local auth switched off: the app sends telemetry with its managed identity and the *Monitoring Metrics Publisher* role. The connection string in the app's settings only says where to send; it isn't enough to send anything.

**Prompts and answers are not recorded.** Agent Framework can put the full messages into spans (`enable_sensitive_data=True`), which makes debugging easier. But conversations contain whatever people type, and traces are read by everyone who operates the system and kept for 30 days or more. It's off; turn it on only where that's acceptable.

**One request, as a trace.** "My laptop CTSO-10442 has a cracked screen. Is it covered?":

| Span | Time | Tokens in / out |
|---|---|---|
| `POST /chat` | 14.1 s | |
| ├ `content_safety shieldPrompt` (the user's message) | 2.1 s | |
| ├ Cosmos DB read | 0.2 s | |
| └ `invoke_agent contoso-helpdesk` | 11.8 s | **4,119 / 574** |
|   ├ `chat`: decides to check the warranty | 1.9 s | 1,179 / 31 |
|   ├ `execute_tool check_laptop_warranty` | 0.0 s | |
|   ├ `chat`: decides to search the policies | 2.7 s | 1,294 / 105 |
|   ├ `execute_tool search_policies` (AI Search 0.5 s) | 1.1 s | |
|   ├ `content_safety shieldPrompt` (the search result) | 1.9 s | |
|   └ `chat`: writes the answer | 4.1 s | 1,646 / 438 |

Things you can only see this way:

- **It took three model calls**, because the model called the tools one after the other. In v5 the same question took two.
- **Each model call re-reads everything so far**, so input tokens grow with every step: 1,179, then 1,294, then 1,646.
- **The safety checks cost 4 of the 14 seconds.** Measured by hand with `curl` they looked like 0.3 s each; inside real requests the average is 1.2 s, 2.3 s at the 95th percentile. That's the kind of thing tracing is for.

**Tokens and cost in every response.**

```json
"usage": {"input_tokens": 4119, "output_tokens": 574, "estimated_cost_usd": 0.002178},
"trace_id": "b6fed1b4e280666932d388a632a99fb6"
```

The token counts are for the whole turn, every model call in the loop: the three calls above add up to exactly 4,119 in. Reasoning tokens are part of `output_tokens`, as they're billed as output. The cost uses `PRICE_INPUT_PER_MILLION` and `PRICE_OUTPUT_PER_MILLION`, defaulting to gpt-5-mini's list prices ($0.25 and $2.00 per million tokens). Prices change, so check them. The estimate covers the chat model only, not embeddings, Content Safety or the services' hourly costs.

`trace_id` (the `X-Trace-Id` header on `/chat/stream`) finds the request in Application Insights: *Transaction search*, paste the id. v12 links user feedback to it.

**Attributes on each request.** The request span carries `helpdesk.user_id`, `session_id`, `status` (`answered` or `approval_required`), `tool_calls`, `withheld`, `input_tokens`, `output_tokens`, `cost_usd`, and `blocked` when Prompt Shields stopped a message. So you can ask questions across requests. One catch on the way: inside an endpoint, the *current* span is FastAPI's inner `fastapi.endpoint` span, not the request, so the first version put all attributes there. A small middleware now remembers the request's own span.

## Queries

In the portal: Application Insights → *Logs* (or the Log Analytics workspace). These are the queries used to check this iteration:

```kusto
// Each request: time, tokens, cost, outcome
AppRequests
| where Name startswith "POST /chat"
| project TimeGenerated, Name, ms = round(DurationMs), status = tostring(Properties["helpdesk.status"]),
          tokens_in = toint(Properties["helpdesk.input_tokens"]), tokens_out = toint(Properties["helpdesk.output_tokens"]),
          cost_usd = todouble(Properties["helpdesk.cost_usd"]), blocked = tostring(Properties["helpdesk.blocked"]),
          OperationId
| order by TimeGenerated desc

// Cost per user per day
AppRequests
| where isnotempty(Properties["helpdesk.cost_usd"])
| summarize requests = count(),
            tokens = sum(toint(Properties["helpdesk.input_tokens"]) + toint(Properties["helpdesk.output_tokens"])),
            cost_usd = round(sum(todouble(Properties["helpdesk.cost_usd"])), 4)
  by user = tostring(Properties["helpdesk.user_id"]), day = bin(TimeGenerated, 1d)

// Where the time goes
AppDependencies
| where Name startswith "chat" or Name startswith "execute_tool" or Name startswith "content_safety"
     or Name startswith "ContainerProxy" or Name startswith "invoke_agent"
| summarize calls = count(), avg_ms = round(avg(DurationMs)), p95_ms = round(percentile(DurationMs, 95)) by Name
| order by avg_ms desc

// Safety events, with the trace to look at
AppTraces
| where Message startswith "safety:"
| project TimeGenerated, Message, OperationId
```

From a test session of 12 agent runs: model calls averaged 2.7 s (21 calls), Prompt Shields 1.2 s (19 calls), `search_policies` 0.8 s, Cosmos DB 40–110 ms. Eight requests cost $0.007 together.

## Demo script

Set up as in v7 (`URL`, `CID`, `TOKEN`, `chat`).

1. **Cost per question.**
   ```bash
   chat chat '{"question": "How do I connect a second monitor?"}' | jq '.usage, .trace_id'
   chat chat '{"question": "My laptop CTSO-10442 has a cracked screen. Is it covered?"}' | jq '.usage, .trace_id'
   ```
   The second uses three to four times the tokens: each tool round is another model call that re-reads the conversation.
2. **One request, end to end.** In the portal: Application Insights → *Transaction search* → paste the second `trace_id`. Open it: the timeline shows every model call, tool, search and safety check, nested. Click a `chat` span for its token counts.
3. **Where the time goes.** Run the "Where the time goes" query. Compare model calls, safety checks and the database.
4. **A blocked attack, found.** Send a jailbreak (v8 demo step 1), then run the "Safety events" query, and open its `OperationId`.
5. **Application map.** Application Insights → *Application map*: `contoso-helpdesk-api` and everything it calls.

Allow a minute or two for telemetry to arrive.

| Problem | Fixed in |
|---|---|
| We can see what happened, but not whether answers were *good*; nothing measures quality | v10: evaluations |
| Nobody is alerted when cost or latency jumps; the numbers have to be looked at | v11: budgets and limits; alerts on these queries |
| The cost estimate leaves out embeddings, Content Safety and fixed hourly costs | Azure Cost Management for the full bill |
| Prompt Shields adds 1–2 s to many requests; it's now visible, not yet improved | v11: e.g. run checks in parallel, cache results for unchanged documents |
| Users can't tell us an answer was wrong, and there's no link from a complaint to its trace | v12: feedback linked to trace ids |
