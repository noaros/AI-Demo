# v11: Resilience and cost control

**Goal:** keep the agent answering, or failing clearly and quickly, when there's more demand than the model can serve. Also stop one user, or one runaway conversation, from using up capacity and money meant for everyone. Until v10 the app called a single Azure OpenAI deployment in a single region, with the SDK's defaults: a 10-minute timeout, and retries that wait as long as Azure says.

## What's included

```
AI-Demo/
├── infra/
│   ├── gateway.bicep        # new: API Management (the AI gateway), a backend per region, the backend pool
│   ├── gateway-policy.xml   # new: what the gateway does with each model call
│   └── resources.bicep      # + a second Azure OpenAI account in another region, with the same deployments
├── app/
│   ├── main.py              # model calls go through the gateway; turn deadline; session budget; clear 429/503/504

│   └── memory.py            # sessions count the tokens they've used

└── evals/run.py             # evals bypass the gateway
```

Run `azd up` (new resources: API Management takes about 3 minutes to create).

## What changed

### The AI gateway

The app no longer calls Azure OpenAI. It calls **Azure API Management** (APIM), which forwards each call to a model. Because every model call passes through one place, rules for all of them can live there instead of in every app that uses the models. Microsoft calls APIM used this way an *AI gateway*. The Basic v2 tier is enough; it's billed by the hour, like AI Search.

For each call, `infra/gateway-policy.xml` does four things:

1. **Checks who's calling.** The caller needs an Entra ID token for Azure OpenAI, and its object id must be on a list (the app's managed identity, and you). Anyone in the tenant can get such a token, so the audience alone isn't enough. No subscription keys: they would be secrets.
2. **Limits tokens per user.** `llm-token-limit` counts tokens per minute for each user (`GATEWAY_TOKENS_PER_MINUTE`, default 10,000: two or three questions a minute). It estimates a request's prompt tokens before forwarding it, so a user over the limit gets a 429 before any model runs. The app says who each call is for in an `x-user-id` header, the signed-in user's id. The gateway can trust that header because only the app (and you) may call it.
3. **Signs in to Azure OpenAI as itself.** The gateway has its own managed identity with *Cognitive Services OpenAI User* on both accounts. The caller's token never reaches the model.
4. **Fails over between regions.** Two backends, `eastus2` (priority 1) and `swedencentral` (priority 2), in a **backend pool**. Each backend has a **circuit breaker**: after a 429 or 5xx it's taken out of rotation for 30 seconds, or for as long as its `Retry-After` says. The policy's `<retry>` then sends the same request again, now to the other region. The user gets a normal answer.

The response says which region answered (`x-served-by`); the app logs it and puts it on the request's trace as `helpdesk.served_by`.

The models' deployments are unchanged: 10,000 tokens per minute each, so 20,000 in total. **The per-user limit must be lower than that total**, or one user can still use up everyone's capacity. The first version had 20,000 per user, and one user's burst used up both regions.

### In the app

| Control | Where | What it prevents |
|---|---|---|
| Steps per question: 5 model calls | `agent.py` (since v6) | An agent calling tools in a loop forever |
| 30 s per model call (was 10 minutes) | `main.py`, `MODEL_CALL_TIMEOUT` | A hung call holding a request open |
| Retries: 2, with backoff, except where the gateway says not to | OpenAI SDK + gateway's `x-should-retry: false` | Retrying a limit that won't lift for a minute |
| 60 s per question, everything included | `main.py`, `TURN_TIMEOUT_SECONDS` | A question that never ends; returns 504 |
| 100,000 tokens per conversation | `main.py` + `memory.py`, `SESSION_TOKEN_BUDGET` | A conversation (or a script) that goes on forever; returns 429 |
| Clear errors with `Retry-After` and `trace_id` | `main.py`, exception handlers | Opaque 500s that make clients retry immediately |

Every model call fits inside the turn deadline: 5 steps × (30 s + retries) is more than 60 s, so the deadline is what bounds a question.

### Measured: ten questions at once, from one user

`python -m scripts.burst 10` on Azure. Each question takes about 3,000–5,000 tokens across the agent's model calls.

| | v10: one region, SDK defaults | v11: gateway, 10,000 tokens/min per user | v11: per-user limit lifted to 100,000 |
|---|---|---|---|
| Answered | 2 | 3 | 5 |
| Failed | 8 × **500** after **46 s** | 7 × **429** after 3–6 s, "try again in N seconds" | 5 × **503** after 5 s, "busy, try again in 26 seconds" |
| Regions that answered | eastus2 | eastus2 + swedencentral | eastus2 + swedencentral (10 and 21 model calls) |

v10 fails slowly and opaquely: the SDK retried the 429s from eastus2 (*"Your requests to gpt-5-mini for chat in eastus2 have exceeded token rate limit"*), waiting as told, until the request failed anyway, and the user got a 500. v11 serves more, and fails fast with something a client can act on. Note that **failover doesn't create capacity, it borrows another region's**: past 20,000 tokens a minute, both circuits open and the gateway answers 503 itself.

### What building it taught

**An exhausted pool says "wait", and the SDK waits.** In the first v11 version, half the burst ended at the 60-second deadline. When every backend's circuit is open, the gateway answers **503 with `Retry-After` as a date**, about 30 seconds away. The OpenAI SDK honours that, sleeping and retrying, until the turn deadline killed the request. The gateway now adds `x-should-retry: false` to its own 429s and 503s (the SDK checks that header first), and the app turns them into a 429 or 503 for the client with `Retry-After` in seconds.

**A deadline only interrupts at an `await`.** With a 3-second deadline, the 504 came after 5.8 seconds: some tools call Cosmos DB and AI Search with synchronous clients, and nothing can be cancelled until they return. The streaming endpoint has no turn deadline at all (cancelling between chunks would break the response mid-sentence); only its per-call timeouts apply.

**Evals shouldn't go through the gateway.** They run every case as one of two test users, who would hit the per-user limit within a minute. `evals/run.py` calls Azure OpenAI directly: evals measure the agent, not the gateway.

### Why there's no semantic cache

A semantic cache stores answers and returns a stored one when a new question is *similar* (by embedding) to an old one. It saves a lot for FAQ bots, where an answer depends only on the question. Here it doesn't, for two reasons:

- **Answers depend on who's asking.** "What's the status of my ticket?" from two users must give two answers; a cache keyed on the question gives the second user the first user's ticket. That's a data leak, not just a wrong answer.
- **Answers depend on live data.** Tool results (ticket status, warranty) change. A cached answer is a snapshot that the agent was designed (v6) not to trust.

Caching is safe only for parts that depend on nothing but the question, such as the policy search results or their embeddings. At this traffic, that wouldn't justify the Azure Managed Redis it needs.

## Demo script

With the azd values exported (`set -a; eval "$(azd env get-values)"; set +a`):

1. **Watch v10 break.** On `v10`, `python -m scripts.burst 10`: most questions fail with a 500 after about 45 seconds. Find out why in the container logs: `429 - Your requests to gpt-5-mini for chat in eastus2 have exceeded token rate limit`.
2. **Watch v11 hold.** On `v11`, the same command: a few answers, the rest a 429 within seconds, each with "try again in N seconds". Run it again after the time it says.
3. **Who answered?** In Application Insights:
   ```kusto
   requests | where timestamp > ago(30m) and name has "chat"
   | summarize count() by resultCode, tostring(customDimensions["helpdesk.blocked"]), tostring(customDimensions["helpdesk.served_by"])
   ```
4. **Failover.** Lift the per-user limit, so only the models' own limits apply:
   ```bash
   azd env set GATEWAY_TOKENS_PER_MINUTE 100000 && azd provision    # about 1.5 minutes
   python -m scripts.burst 10
   ```
   Both regions answer, and what's beyond both gets a 503 within seconds. Set it back to 10000 afterwards.
5. **Only the app may call the gateway.** `curl -X POST $AI_GATEWAY_ENDPOINT/openai/v1/chat/completions` without a token, or with a token for another audience (`az account get-access-token`): 401.
6. **Session budget.** Locally, `SESSION_TOKEN_BUDGET=6000`: the third question in a conversation gets *"This conversation has used its budget of 6000 tokens: start a new one"*.
7. **Turn deadline.** Locally, `TURN_TIMEOUT_SECONDS=3`: a question that needs a tool gets a 504.

## What's still wrong

| Problem | Fixed in |
|---|---|
| Only the model fails over. Cosmos DB, AI Search, Container Apps and the gateway itself are in one region each | Multi-region deployment of the whole app: a bigger step, and twice the cost |
| A turn that fails partway (deadline, limit) isn't charged to the session budget; the gateway still counts its tokens | Charge per model call, not per turn |
| A user who hits the limit in the middle of a turn loses that turn's work | Check the remaining tokens (`x-ratelimit-remaining-user-tokens`) before starting a turn |
| The streaming endpoint has no turn deadline, and a gateway 429 mid-stream ends the stream without explanation | Send a final error line on the stream |
| Synchronous Cosmos DB and AI Search calls block the event loop: the deadline overshoots, and one replica serves fewer requests at once | Async clients (`azure.cosmos.aio`, `azure.search.documents.aio`) |
| API Management Basic v2 is billed by the hour (about US$0.20), used or not | Tear down after demos; in production, one gateway is shared by many apps |
| Nobody learns from bad answers | v12: feedback linked to traces, red teaming, failures become eval cases |
